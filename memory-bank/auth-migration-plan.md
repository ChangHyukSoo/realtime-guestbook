# 로그인·회원가입 기반 인증·인가 및 마이그레이션 계획

갱신: 2026-10-27. 상태: 애플리케이션·후속 SQL·운영 스크립트 구현 및 로컬 검증 완료, 원격 적용·실제 메일/Storage/Realtime 검증 전. 실행 현황은 `progress.md`, 적용 절차는 루트 `README.md`를 따른다.

## 1. 요구사항 변경과 기본안

사용자 지시에 따라 기존 “로그인 없이 닉네임 사용” 및 앞선 익명 인증 제안을 대체한다. 로그인·회원가입 UI부터 구현하고 Supabase Auth 계정으로 방명록을 이용한다. 기존 캔버스·댓글·실시간 기능은 재사용한다.

이번 계획의 기본안은 이메일·비밀번호 가입, 이메일 확인, 로그인, 로그아웃, 비밀번호 재설정이다. 비로그인 사용자는 `/login`으로 보내고 목록·상세·작성·이미지 읽기 모두 로그인 사용자에게 허용한다. 공개 열람과 소셜 로그인은 후속 확장으로 둔다. 화면 접근 범위와 이메일 방식은 사용자 요청을 구체화한 설계 기본값이다.

닉네임은 회원가입 때 정하는 표시 이름이며 신원이나 권한 기준으로 쓰지 않는다. 댓글마다 닉네임을 다시 입력하는 기존 UI는 계정 닉네임 표시로 바꾼다. 닉네임 중복은 허용하며 사용자 식별은 UID로 한다. 사용자 수정·삭제 기능과 관리자 화면은 1차 범위에 추가하지 않는다.

## 2. 현재 구조와 변경 지점

| 위치 | 현재 | 목표 |
| --- | --- | --- |
| `src/app` | 목록·작성·상세 세 라우트 | 공개 인증 라우트와 보호된 방명록 라우트 그룹 |
| `src/lib/supabase.ts` | 공개 키 브라우저 클라이언트, Auth 없음 | 브라우저/요청별 서버 클라이언트 분리, 쿠키 세션 |
| `src/components/guestbook.tsx` | Canvas·조회·저장·댓글·구독 집중 | 인증 UI 분리, 계정 닉네임 사용, 권한 오류·세션 만료 처리 |
| 최초 SQL | `anon` SELECT/INSERT, 작성자 컬럼 없음 | 회원 프로필·작성자 UID, 회원 전용 읽기/등록 |
| Storage | public 버킷, `<uuid>.png`, DB에 공개 URL 저장 | private 버킷, `<uid>/<entry-id>.png`, 객체 키와 서명 URL |
| 데모 | 환경 변수 미설정 시 자동 localStorage 모드 | 운영 설정 누락은 오류 처리, 데모는 명시적 개발 모드로 분리 |

2026-10-27 원격 재조회 결과 `public.guestbook`(0행, RLS 꺼짐) 외에 `guestbooks` 1행, `comments` 2행과 공개 이미지 1개가 있다. Auth 사용자와 기록된 migration은 0개다. 최초 SQL은 이미 수동 적용된 것으로 보이며 기존 스키마와 이력을 대조하기 전 재실행하지 않는다. 별도 `guestbook`은 사용처 확인 없이 자동 변경하지 않는다.

## 3. 화면과 사용자 흐름: 첫 구현 단계

| 경로 | UI 및 동작 |
| --- | --- |
| `/login` | 이메일·비밀번호, 로그인, 회원가입 이동, 비밀번호 찾기 |
| `/signup` | 이메일·닉네임·비밀번호·확인, 가입, 로그인 이동 |
| `/signup/check-email` | 확인 메일 발송 안내, 재발송 및 재시도 제한 안내 |
| `/auth/confirm` | 서버에서 메일 token hash와 허용된 유형 검증, 세션 설정 후 안전한 내부 경로 이동 |
| `/forgot-password` | 재설정 메일 요청, 계정 존재 여부를 드러내지 않는 완료 안내 |
| `/reset-password` | 검증된 복구 세션에서 새 비밀번호·확인 입력 |
| `/`, `/write`, `/guestbooks/[id]` | 로그인 필수, 상단 닉네임·로그아웃 제공 |

첫 방문 → 로그인 → 회원가입 → 이메일 확인 안내 → 확인 링크 → 프로필 준비 확인 → 목록으로 이동한다. 기존 회원은 로그인 후 원래 요청했던 안전한 내부 경로로 돌아간다. 가입 응답에 세션이 없는 이메일 확인 대기 상태를 성공적인 로그인으로 처리하지 않는다.

먼저 기존 아이보리·세이지 UI와 일관된 인증 화면과 입력 검증을 만든다. `ui_plan.png`는 방명록 화면만 제공하므로 인증 화면은 새 화면으로 설계한다. UI 단계에서는 mock을 개발/테스트에만 사용하고 인증 완료로 표시해 실제 보호 라우트를 열지 않는다.

공통 상태: 필드 오류, 서버 오류, 제출 중 버튼 잠금, 메일 재발송 대기, 만료·재사용 링크, 로그인 실패, 모바일 레이아웃, 키보드 포커스와 자동완성 지원. 비밀번호는 로그·URL·localStorage·초안에 저장하지 않는다.

## 4. 세션과 라우트 보호

- `@supabase/ssr` 추가를 계획하고 `src/lib/supabase/client.ts`, `server.ts`로 분리한다. 서버 클라이언트는 요청별 생성하고 쿠키를 연결한다. 기존 SDK/Next.js 버전과 호환되는 API를 확인한 후 의존성 버전을 확정한다.
- Next.js 16의 `src/proxy.ts`에 쿠키 갱신과 기본 리다이렉트를 구성한다. Proxy만을 인가 경계로 삼지 않고 서버 페이지·Server Action·Route Handler에서 검증된 사용자로 접근을 확인한다. 서버에서 `getSession()` 결과만 신뢰하지 않는다.
- `(auth)` 공개 그룹과 `(guestbook)` 보호 그룹으로 구성하되 기존 URL은 유지한다. 인증된 사용자의 로그인/가입 진입은 목록으로 보낸다. 복구 세션의 재설정 화면은 별도 허용한다.
- 인증 확인/복구 링크는 허용한 목적과 유형만 처리한다. `next`는 허용된 내부 경로만 받아 외부 URL·프로토콜 상대 경로로의 이동을 거부한다. 운영/개발 Site URL·Redirect URL·메일 템플릿을 일치시킨다.
- 서버 데이터 접근은 사용자 JWT를 전달해 RLS를 적용한다. 사용자별 응답을 공유 캐시에 넣지 않는다. 쿠키 기반 변경 요청은 Server Action 또는 출처/CSRF 검증을 적용한다.
- 로그아웃 시 세션·메모리 데이터·서명 URL과 Realtime 구독을 정리한다. 만료 시 캔버스/댓글 초안을 비민감 데이터로 현재 탭에 보존하고 재로그인 후 복원한다. 초안은 사용자별로 분리하고 다른 계정으로 자동 제출하지 않는다. 명시적 로그아웃은 작성 내용 폐기를 확인한다.
- 기존 브라우저 localStorage 세션이 존재하면 쿠키 세션과 혼용하지 않도록 전환 후 재로그인을 요구한다. 익명 자동 로그인은 사용하지 않고 프로젝트의 익명 로그인 설정도 확인한다.

## 5. 데이터 모델과 인가

| 리소스 | 비로그인 | 로그인 회원 |
| --- | --- | --- |
| 목록·상세·댓글·이미지 읽기 | 차단 | 허용 |
| 방명록·댓글 등록 | 차단 | 본인 UID로만 허용 |
| 이미지 업로드 | 차단 | 본인 경로에만 허용 |
| 데이터 수정·삭제·작성자 변경 | 차단 | 차단 |
| 내 프로필 조회 | 차단 | 본인만 허용 |

- `profiles(id uuid PK references auth.users(id), nickname text, created_at)`를 추가한다. 이메일·비밀번호를 복제하지 않는다. 닉네임은 공백 제외 1~20자 제약을 유지한다.
- 가입 시 메타데이터의 닉네임을 검증한 최소 권한 트리거로 프로필을 생성한다. 고정 `search_path`와 직접 실행 차단을 적용한다. 누락/실패 계정의 복구 경로와 프로필 없을 때 작성 차단을 정의한다. 프로필 수정 UI와 UPDATE 권한은 이번 범위에 추가하지 않는다.
- 두 콘텐츠 테이블에 nullable `author_id references auth.users(id) on delete set null` 및 인덱스를 추가한다. 기존 데이터는 소유자를 모르므로 NULL로 보존한다. 신규 INSERT는 `default auth.uid()`와 RLS로 NULL·타인 UID를 거부한다.
- 댓글의 `nickname`은 작성 당시 프로필 닉네임의 스냅샷으로 유지한다. DB 트리거에서 프로필 값을 설정하여 클라이언트의 임의 닉네임 제출을 신뢰하지 않는다. 작성 시각은 DB가 설정하고 클라이언트 시간 위조를 막는다.
- 테이블 SELECT/INSERT 권한과 정책은 `authenticated`에 명시한다. 익명 Auth 사용자는 같은 DB 역할을 사용하므로 비익명 조건도 적용하여 남아 있는 익명 계정 접근을 차단한다. 기존 `anon` 읽기/쓰기 GRANT·정책을 제거한다. 새 정책 추가만으로 공개 정책이 사라지지 않는다.
- 이메일 확인을 활성화하고 미확인 계정은 세션이 발급되지 않는 구성으로 검증한다. 역할·닉네임·사용자가 수정하는 메타데이터를 관리자 권한으로 사용하지 않는다.
- 공개 UID 조회는 같은 계정의 글을 연결할 수 있으므로 회원 간 노출 범위를 문서화한다. 숨겨야 한다면 컬럼 권한·조회 DTO·Realtime payload를 함께 설계한다.
- 운영자 정리 작업만 서버 비밀 키를 사용하고 브라우저·일반 데이터 접근에는 사용하지 않는다. 계정 삭제 시 콘텐츠를 보존하는 FK 방침은 별도 탈퇴 기능 도입 시 재검토한다.

## 6. Storage·저장·Realtime

- 새 private 버킷(예: `guestbook-images-private`)을 사용하고 PNG/5MB 설정을 명시한다. 객체 INSERT는 본인 폴더와 UUID 파일명만 허용하며 upsert는 금지한다. 회원은 조회할 수 있지만 일반 삭제는 금지한다.
- DB에 `image_object_path`와 필요 시 `image_bucket`을 기록한다. 신규 등록은 UID/방명록 ID와 객체 경로가 일치하고 실제 객체의 `owner_id`가 본인인지 DB 경계에서 검증한다. Storage 내부 테이블을 직접 수정하지 않는다.
- 로그인 상태에서 발급한 짧은 만료 시간의 서명 URL을 표시한다. DB/Realtime에는 서명 URL을 저장하지 않는다. 만료 시 재발급·이미지 로딩 실패 처리를 제공한다. 서명 URL은 만료 전까지 링크 소지자가 사용할 수 있으므로 로그아웃 즉시 무효화되는 것으로 설명하지 않는다.
- 기존 public 버킷 이미지도 private 버킷으로 복사하고 참조를 전환한다. 기존 공개 URL은 UI 로그인만으로 보호되지 않는다. 마지막 단계에서 옛 버킷 public 설정·공개 정책을 닫고 원본/CDN 캐시 만료 범위를 확인한다. 이미 외부로 복사된 이미지는 회수할 수 없다.
- 업로드→DB 등록은 단일 트랜잭션이 아니다. UUID/경로를 재시도 동안 유지하고 응답 유실 시 기존 행 확인 후 재시도한다. 고아 객체는 유예 기간 후 DB 참조를 확인한 서버 작업이 Storage API로 정리한다.
- 기존 INSERT 구독·ID 중복 제거·상세 필터·재조회·해제를 재사용한다. 로그인 후 구독하고 토큰 갱신 때 인증 전달을 확인하며 로그아웃/계정 전환 시 구독과 화면 데이터를 비운다.
- Auth 가입/로그인/메일 요청 제한과 콘텐츠/업로드 남용 제한을 구분한다. 직접 REST로 우회할 수 없는 DB/RPC 제한 또는 검증된 서버 경로를 사용한다. 운영 SMTP, 발신 도메인, 비밀번호 정책, CAPTCHA 필요 여부를 설정·검증한다.

## 7. UI 우선 구현 및 마이그레이션 순서

아래 후속 SQL과 이미지 이전·정리 스크립트를 생성했다. 최초 SQL은 수정하지 않았다. 원격 적용은 전체 백업·스테이징·서버 전용 키 확보 후 진행한다.

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1. 인증 UI | 로그인·가입·확인 안내·찾기·재설정 화면, 계정 메뉴, 폼 상태 구현 | 모바일/키보드/입력 오류 확인, mock과 실제 인증 명확히 분리 |
| 2. 원격 조사 | 스키마·행 수·GRANT·정책·발행·버킷·Auth 설정·적용 이력 확인, DB/객체 백업 | 단일 `guestbook` 매핑과 복원 절차 기록, 스테이징 준비 |
| 3. 기반 확장 | `202610270001_member_expand.sql`: profiles·작성자·객체 경로·인덱스·트리거, 회원용 정책 추가, private 버킷 준비 | 기존 행 보존, 빈 DB 설치와 기존 DB 업그레이드 성공 |
| 4. 실제 Auth 연동 | SSR 클라이언트·쿠키 갱신·확인 링크·재설정·보호 라우트·SMTP 연결 | 가입→메일 확인→로그인→로그아웃→복구 실제 성공 |
| 5. 방명록 통합 | 프로필 닉네임, 회원 작성·업로드·서명 URL·구독·실패 복원 연결 | A/B 계정에서 등록·실시간 반영, 위조·만료 처리 확인 |
| 6. 기존 이미지 전환 | `202610270002_member_backfill.sql` 및 Storage API 스크립트: 기존 URL 검증, 객체 복사, 경로 매핑 | 행/객체 수·체크섬 또는 크기·댓글 FK·이미지 참조 대조 |
| 7. 정책 강제·출시 | `202610270003_member_enforce.sql`: anon GRANT/정책 제거, 기존 공개 이미지 접근 종료, 프로덕션 배포 | 비로그인 직접 API/Storage 차단, 구버전 탭 차단, 전체 회귀 통과 |
| 8. 안정화 | 오류·메일 전달·고아 파일·구독 관측, 호환 URL 컬럼 축소 여부 결정 | 관측 기간 후 데이터 보존 확인과 문서 정합성 확보 |

UI 구현은 첫 단계부터 진행할 수 있다. 원격 데이터 변경은 현황 조사와 스테이징 이후에 수행한다. 단계 3~7의 호환 기간에는 기존 공개 권한이 남을 수 있으므로 회원 전용 전환 완료로 보지 않는다. 운영 배포는 쓰기 중지 시간을 정해 이미지 최종 동기화·클라이언트 배포·정책 강제를 묶고, 직접 API도 DB/Storage에서 통제한다.

기존 콘텐츠를 새 가입자에게 닉네임으로 자동 귀속시키지 않는다. 로컬 데모 데이터는 운영으로 자동 이전하지 않는다. 과거 원격 0행 기록만으로 `guestbook`을 삭제하지 않는다. 최초 SQL의 테이블/정책/publication 생성은 재실행에 안전하지 않으므로 이력을 확인한다.

## 8. 검증과 출시 기준

- UI: 이메일·닉네임·비밀번호/확인 검증, 제출 중 중복 방지, 일반화된 오류, 모바일·접근성 확인.
- 계정: 실제 이메일 확인/재발송, 미확인 로그인, 만료·재사용 링크, 복구 메일과 비밀번호 변경, 로그아웃·새로고침·여러 탭·만료 확인. 로컬 메일 테스트와 운영 SMTP 전달을 구분한다.
- 접근: 비로그인 직접 URL 및 REST/Storage 읽기·쓰기 모두 차단, 회원 정상 접근, 익명 Auth 계정도 차단, 안전하지 않은 `next` 거부, 인증 캐시 누출 없음.
- 인가: A가 B의 UID·폴더·객체·닉네임을 위조하면 거부/서버값 강제, NULL 작성자 신규 등록·임의 시간·과대/잘못된 파일·외부 이미지 URL 차단. RLS 테스트는 서비스 키가 아닌 각 사용자 JWT로 수행.
- 보존: 기존 author_id NULL 행·이미지·댓글 표시 유지, 고아 객체 정리의 참조 보호, 응답 유실 재시도 중복 없음, 재로그인 후 초안 복원과 계정 전환 격리.
- 실시간: 로그인한 두 브라우저에서 새 글/댓글이 한 번씩 표시, 상세 이동·로그아웃·만료·재접속 후 구독 정리와 복구 확인.
- 이미지: 서명 URL 갱신, 비로그인 신규 발급 거부, 옛 public URL 접근 종료와 캐시 제한 확인.
- 마이그레이션: 빈 DB 및 원격 복제 환경의 업그레이드/롤백 확인, 행·파일·FK·정책·버킷·발행 대조.
- 코드 변경 후 `npm run typecheck`, `npm run build`, 인증·방명록 Playwright 회귀 수행. 외부 메일/DB/Storage 미실행 검증은 별도 미완료 기록.

## 9. 롤백과 운영

확장 컬럼·옛 이미지 원본·매핑 목록은 검증 기간 동안 유지한다. 정책 강제 이후 인증 없는 구버전으로 단독 복귀하지 않는다. 마지막 정상 회원 인증 버전 또는 읽기/쓰기 차단 점검 화면으로 복구하고 공개 권한을 자동 재개방하지 않는다. 옛 공개 버킷으로의 복귀도 회원 전용 요구사항과 충돌하므로 기본 롤백에서 제외한다.

DB와 Storage는 별도 복원 대상이다. 복원 시 전환 후 신규 데이터 손실 범위를 확인한다. Auth 실패율·메일 전달·등록 성공률·RLS/Storage 거부·고아 객체·Realtime 연결을 관측하고 토큰·비밀번호·비밀 키는 로그에 남기지 않는다.

Auth 화면·SSR 쿠키 세션·페이지별 보호·회원 저장·프로필 정책·private 이미지 처리와 SQL/운영 스크립트를 구현했다. 라우트 그룹 이동 대신 기존 세 URL의 서버 페이지에서 공통 `requireMember()`를 호출한다. PGlite 및 로컬 HTTP fixture 검증 범위를 실제 Supabase 통합 검증과 구분한다. 확장 SQL부터 검증 트리거가 비회원 쓰기를 거부하므로 원격 전환 시 확장 단계부터 쓰기를 중지해야 한다.
