## User Scenarios & Testing *(mandatory)*

### User Story 1 - 나를 표현하는 닉네임 설정 (Priority: P1)

로그인한 회원은 방명록에서 프로필 설정으로 이동해 현재 닉네임을 확인하고 원하는 이름으로 변경한다.

**Why this priority**: 글 작성자를 구분하고 기억할 수 있는 기본적인 정체성을 제공한다.

**Independent Test**: 사진 없이 닉네임만 변경하고 재접속하여 저장된 이름과 작성자 표시를 확인한다.

**Acceptance Scenarios**:

1. **Given** 신규 회원이 가입을 완료했을 때, **When** 처음 로그인하면, **Then** 별도 프로필 입력 없이 기본 닉네임과 기본 아바타로 활동할 수 있다.
2. **Given** 로그인한 회원이 방명록에 있을 때, **When** 프로필 설정을 선택하면, **Then** 자신의 현재 닉네임과 사진을 확인하고 편집할 수 있다.
3. **Given** 유효하고 중복되지 않은 닉네임을 입력했을 때, **When** 저장하면, **Then** 성공 안내가 표시되고 다시 접속해도 변경한 이름이 유지된다.
4. **Given** 빈 값, 공백만 있는 값, 20자를 넘는 값 또는 다른 회원과 중복되는 이름일 때, **When** 저장하면, **Then** 원인을 안내하고 기존 프로필과 입력 내용을 보존한다.

---

### User Story 2 - 프로필 사진 등록과 교체 (Priority: P1)

회원은 PC나 모바일에서 자신을 표현하는 이미지를 선택하여 저장하고 이후 다른 사진으로 교체한다.

**Why this priority**: 사진은 닉네임과 함께 작성자를 빠르게 알아보게 하는 핵심 수단이다.

**Independent Test**: 닉네임을 변경하지 않고 사진만 등록·교체한 뒤 재접속해 사진을 확인한다.

**Acceptance Scenarios**:

1. **Given** 사진이 없는 회원일 때, **When** 허용되는 사진을 선택하고 저장하면, **Then** 기본 아바타가 선택한 사진으로 바뀌며 재접속 후에도 유지된다.
2. **Given** 기존 사진이 있는 회원일 때, **When** 새 사진을 저장하면, **Then** 새 사진이 표시되고 기존 사진이 현재 사진으로 다시 나타나지 않는다.
3. **Given** 허용되지 않는 형식, 손상된 파일 또는 5MiB를 초과하는 파일일 때, **When** 저장을 시도하면, **Then** 이유를 안내하고 기존 닉네임과 사진을 변경하지 않는다.
4. **Given** 닉네임과 사진을 함께 변경 중일 때, **When** 저장에 실패하면, **Then** 성공한 것으로 안내하지 않고 기존 프로필과 현재 화면의 입력·선택 파일을 유지하여 재시도할 수 있다.

### User Story 3 - 방명록에서 작성자 알아보기 (Priority: P1)

로그인한 회원은 방명록 목록·상세·댓글에서 작성자의 현재 닉네임과 프로필 이미지를 보고 동일한 작성자를 알아본다.

**Why this priority**: 프로필 설정을 실제 커뮤니티 내 작성자 인지로 연결한다.

**Independent Test**: 서로 다른 두 회원이 작성한 글과 댓글을 열어 각 회원의 닉네임과 사진이 일관되게 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 회원이 작성한 글과 댓글이 있을 때, **When** 목록·상세·댓글을 조회하면, **Then** 해당 작성자의 현재 닉네임과 사진을 함께 볼 수 있다.
2. **Given** 작성자가 프로필을 변경했을 때, **When** 기존 글과 댓글을 다시 조회하면, **Then** 변경된 프로필이 표시되며 작성자 귀속은 유지된다.
3. **Given** 다른 창에서 변경된 프로필이 있을 때, **When** 열린 방명록 창에 포커스를 되돌리거나 다른 창에서 저장한 뒤 30초 이내가 되면, **Then** 정상 네트워크 환경에서 최신 프로필이 반영된다.
4. **Given** 사진이 없거나 불러오기에 실패했을 때, **When** 작성자를 표시하면, **Then** 기본 아바타와 닉네임으로 작성자를 계속 구분할 수 있다.

### Edge Cases

- 같은 회원의 다른 창에서 편집 시작 이후 프로필이 저장되었으면, 나중 저장은 변경 항목이 달라도 전체를 거부한다. 먼저 저장된 프로필을 유지하고 최신 정보 확인을 안내하며, 현재 입력과 선택 파일은 보존한다. 최신 정보를 확인하기 전 재제출로 덮어쓰지 않는다.

- 앞뒤 공백을 제거하고 영문 대소문자를 구분하지 않아 동일한 이름은 중복으로 처리한다. 자신의 기존 이름을 유지하는 저장은 허용한다.
- 두 회원이 같은 이름을 동시에 저장하면 한 회원만 성공하고 다른 회원은 입력을 보존한 채 중복 안내를 받는다.
- 기본 닉네임의 길이 초과나 충돌은 20자 이내 고유한 기본 이름을 생성하여 해결한다. 기존 회원의 이름은 자동 변경하지 않는다.
- 이미지 없이 닉네임만 저장하면 기존 사진을 유지한다. 선택만 하고 저장하지 않은 변경은 다른 화면이나 회원에게 반영하지 않는다.
- 저장 중 연속 클릭은 중복 변경을 만들지 않는다. 로그인 만료 시 재로그인을 안내하고 현재 화면의 입력을 유지한다. 재로그인 이동 후 파일 복원까지는 보장하지 않는다.
- 회원 연결이 없는 기존 글은 기본 방문자 이름과 아바타를, 기존 댓글은 작성 당시 이름과 기본 아바타를 표시하며 임의로 회원에게 연결하지 않는다.
- 프로필 정보 자체를 가져오지 못하면 방명록 본문은 유지하고 임시 기본 표시를 사용한다. 다른 회원의 프로필로 대체하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 회원가입 시 별도 프로필 입력 없이 기본 프로필을 생성해야 한다. 기본 닉네임은 이메일의 @ 앞부분에서 생성하되 최대 20자를 지키고 충돌 시 고유 접미사를 붙여야 한다. 이메일 전체는 작성자 정보에 노출하지 않아야 한다.
- **FR-002**: 로그인한 회원은 PC와 모바일 방명록에서 자신의 프로필 설정에 진입하여 현재 정보 확인과 수정을 할 수 있어야 한다.
- **FR-003**: 닉네임은 앞뒤 공백 제거 후 1~20자로 제한하고, 대소문자를 구분하지 않는 다른 회원과의 중복을 거부해야 한다. 동시 저장에도 이 규칙이 유지되어야 한다.
- **FR-004**: 회원은 PNG, JPEG, WebP 형식의 유효한 이미지 중 최대 5MiB(5,242,880바이트)를 선택하여 프로필 사진을 등록·교체할 수 있어야 한다. 형식 불일치와 손상된 이미지는 거부해야 한다. 사진 등록·교체의 모든 저장 경로는 서버의 전체 이미지 검증을 거쳐야 하며 직접 업로드나 직접 저장 요청으로 이를 우회할 수 없어야 한다.
- **FR-005**: 닉네임만, 사진만 또는 둘 모두를 한 번에 저장할 수 있어야 한다. 성공한 변경은 재접속 후에도 유지되고 사진 미선택은 기존 사진을 보존해야 한다.
- **FR-006**: 시스템은 저장 중 상태와 성공·실패 결과를 안내하고 중복 제출을 방지해야 한다. 실패 시 기존에 저장된 프로필과 현재 화면의 입력·선택 파일을 보존해야 하며 부분 변경을 완료로 표시해서는 안 된다.
- **FR-007**: 비로그인 사용자는 프로필 조회·수정과 사진 URL 신규 발급을 할 수 없어야 한다. 사진은 private Storage에 저장하고 인증된 회원에게 유효기간 300초의 서명 URL을 발급한다. 이미 발급된 URL은 만료 전까지 소지자가 사용할 수 있으며 로그아웃 즉시 무효화는 보장하지 않는다. 로그아웃 시 앱 메모리의 URL을 제거하고 갱신을 중단한다. 회원은 자신의 프로필만 변경할 수 있고 다른 회원의 닉네임·사진을 변경하거나 삭제할 수 없어야 한다.
- **FR-008**: 로그인한 회원에게 방명록 목록·상세·댓글의 작성자 닉네임과 사진을 표시해야 한다. 표시하는 프로필 정보는 작성자 구분에 필요한 닉네임과 사진으로 제한해야 한다.
- **FR-009**: 프로필 변경은 기존 글·댓글에도 현재 프로필로 반영되어야 하며 작성자 귀속은 바뀌지 않아야 한다. 저장한 화면은 완료 시 변경을 표시하고 다른 활성 창은 정상 네트워크에서 저장 완료 시점부터 30초 이내에 변경된 닉네임과 사진을 표시해야 한다. 사진이 없으면 기본 아바타 표시 완료를 기준으로 한다. 포커스 복귀 시 즉시 갱신을 시작한다.
- **FR-010**: 사진 없음·읽기 실패 시 기본 아바타를 표시해야 한다. 회원 연결이 없는 기존 기록은 Edge Cases의 기존 이름 표시 규칙을 유지해야 한다.
- **FR-011**: 프로필 편집은 키보드로 조작 가능하고 입력 항목에 이름이 있어야 하며 오류를 텍스트로 안내해야 한다. 폭 390px 모바일과 1440px 데스크톱에서 필수 조작이 가려지거나 가로 스크롤을 요구하지 않아야 한다.

- **FR-012**: 같은 회원의 다른 창에서 편집 시작 이후 프로필이 저장되었으면 나중 저장을 전체 거부하고, 먼저 저장된 프로필을 유지해야 한다. 최신 정보 확인을 안내하고 현재 입력·선택 파일을 보존해야 하며, 최신 정보를 확인하기 전 재제출로 덮어쓰지 않아야 한다.

### Key Entities *(include if feature involves data)*

- **회원 프로필**: 한 회원의 현재 공개 표시 정보. 회원 연결, 고유 닉네임, 선택적 프로필 사진을 가진다.
- **프로필 사진**: 프로필에 연결되는 선택적 이미지. 소유 회원, 파일 형식, 크기, 현재 사용 여부를 구분한다.
- **작성자 연결**: 글·댓글과 회원의 관계. 닉네임·사진 변경과 독립적으로 작성자를 유지하며 과거 회원 연결 없는 기록도 표현한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: PC·모바일을 포함한 대표 사용자 5명 중 4명 이상이 별도 도움 없이 프로필 설정에 진입해 닉네임과 사진 저장을 2분 이내 완료한다. 각 사용자에게 유효한 사진을 미리 제공한다.
- **SC-002**: 정상 네트워크 환경의 기능 검증에서 저장·재접속 후 닉네임과 사진 유지, 목록·상세·댓글의 작성자 일치 시나리오가 모두 통과한다.
- **SC-003**: 빈 이름·21자 이름·중복 이름·동시 중복 저장·동일 회원 두 창의 저장 충돌·용량 초과·형식 불일치·손상 이미지·저장 실패·권한 없는 변경 시나리오에서 잘못된 프로필 변경이 0건이다.
- **SC-004**: 두 창을 이용한 검증에서 다른 활성 창은 저장 완료부터 30초 이내에 변경된 닉네임과 사진(없으면 기본 아바타)을 표시한다. 정상 네트워크 검증은 프로필 조회·URL 발급·사진 로딩 전체가 10초 이내인 조건으로 하며, 조회 직후 다른 창이 저장하는 최악 시점과 지연 응답을 포함한다. 비활성 탭·오프라인은 시간 보장 대상에서 제외하고 복귀 시 갱신을 확인한다.
- **SC-005**: 서로 다른 작성자 3명의 글·댓글을 제시했을 때 대표 사용자 5명 중 4명 이상이 닉네임과 사진을 이용해 동일 작성자의 기록을 모두 정확하게 연결한다.

## Assumptions

- 기존 회원 인증과 방명록 글·댓글 기능을 전제로 한다. 가입·로그인 정책 변경은 이번 범위에 포함하지 않는다.
- 기준 요구사항은 [프로필 PRD](../../memory-bank/prd-user-profile.md)와 그 문서의 2026-10-28 세부 기준이다. 기존 5MB 표현은 세부 기준의 5MiB로 해석한다.
- 기존 구현이 있는 기능의 명세를 정리하는 작업이며, 명세 검증 완료는 실제 서비스 검증 완료를 뜻하지 않는다. 구현 현황과 외부 검증 제약은 memory-bank 문서를 따른다.
- 사진 삭제, 자르기·필터, 공개 프로필 페이지, 소개 문구, 회원 검색, 팔로우, 계정 삭제는 이번 범위에서 제외한다.
- 기존 PRD에 없는 오류·경계 조건은 이 명세에 제안 기준으로 명시한다. 저장 실패 복구의 운영 절차는 기존 trouble-shooting.md를 따른다.
- 커뮤니티 유대감은 장기 목표이며 이번 검증에서는 작성자 인지 정확도와 설정 완료율을 대리 지표로 사용한다.

## Revision Decisions (2026-11-02)
